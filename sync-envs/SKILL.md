# Sync Environment Variables

Generate a searchable `envs.md` from project evidence. Document what each variable controls without exposing secret values.

## Scope

1. Use a path or service set supplied by the user.
2. Otherwise, use the nearest Git root; if there is none, use the current workspace or directory as one project.
3. Scan multiple repositories only when requested. Discover them beneath the selected directory and write one consolidated `envs.md` at that directory.

Before scanning each Git repository, run `git pull --ff-only` to include newly added variables. Never rebase, stash, reset, or discard local changes. If the pull fails because the repository is offline, detached, dirty, conflicting, or has no upstream, report it and scan the local checkout unchanged.

Do not clone, install dependencies, or require Git. In Git repositories, prefer tracked files from `git ls-files`. Outside Git, exclude dependency, VCS, cache, build, generated, and secret files. Never scan `.git`, `node_modules`, virtual environments, vendor directories, build outputs, or the generated `envs.md`.

## Discover variables

Detect relevant languages and frameworks from manifests and source files, then search their actual environment access forms. Common examples include:

- JavaScript/TypeScript: `process.env`, `import.meta.env`
- Python: `os.environ`, `os.getenv`, settings classes
- Go: `os.Getenv`, `os.LookupEnv`
- Java/Spring: `System.getenv`, `@Value`, configuration placeholders
- Ruby: `ENV`, `ENV.fetch`
- Shell and containers: parameter expansion, Dockerfile `ARG`/`ENV`, Compose `environment`
- Deployment/config: dotenv examples, Kubernetes manifests, Helm values/templates, and interpolation tokens

Do not stop at generic patterns. Find centralized config helpers or settings objects by tracing raw environment reads, then inspect their definitions and call sites. If configuration resolves tokens such as `${env.NAME}`, scan the files consumed by that resolver. Record dynamic access that cannot be reduced to one name, such as `<PREFIX>_URL`, as a pattern row and explain how names are formed.

Reconcile two sources:

- **Read:** consumed by application or operational code
- **Declared:** supplied by examples, manifests, charts, Compose, CI, or templates

Include variables found in either source. Mark `read but not declared`, `declared but no read found`, and `test-only` in the description. A declaration may be consumed by a framework or external runtime, so do not claim it is unused.

Ignore obvious shell locals and template variables that are not environment inputs. When syntax is ambiguous, inspect context rather than accepting a regex match.

## Derive fields

For each variable or pattern, inspect its definitions and uses:

- **Type:** `string`, `integer`, `number`, `boolean`, `enum`, `url`, `path`, or `json`. Infer from parsing, validation, comparisons, and consumers; use `string` when evidence is insufficient. List enum values in the description.
- **Default:** report the effective code fallback. Use `-` when required or absent. If consumers have different defaults, use `varies` and explain them. Do not treat a deployment-supplied value as an application default.
- **Description:** state the subsystem, external service when relevant, and behavioral effect. Prefix uncertain conclusions with `Inferred:`.

Never emit credentials, tokens, private keys, passwords, or other secret values, including values found in local dotenv files or deployment configuration. For secret-like variables, show a clearly documented non-secret mock default only; otherwise use `-`. Describe the credential's purpose and managed source when known.

## Output

Write `envs.md` with variables sorted alphabetically:

```markdown
# Environment Variables

_Generated by `/sync-envs`: <count> variables across <count> services._

## <service name>

| Variable | Type | Default | Description |
|---|---|---|---|
| `PORT` | integer | `8080` | HTTP listener port. |
```

For one project, use one service section. For multiple services, add a linked service index and one section per repository. Derive stable, unique service names from project metadata, remote basename, or directory name; never hardcode them. End each section with its project-relative path and variable count.

Escape Markdown cells and format safe literal defaults as code. Use `-` without code formatting for absent defaults.

## Update safely

When `envs.md` exists, parse and merge its service sections instead of replacing them blindly:

- add newly discovered rows;
- update evidence-derived type and default;
- preserve a hand-edited description for a variable still present unless it is demonstrably false;
- mark missing variables `⚠️ not found in latest scan` rather than deleting them;
- preserve prose outside generated tables;
- avoid duplicate rows and make repeated runs idempotent.

Report added, updated, unchanged, and flagged counts per service. If the existing document cannot be parsed safely, do not overwrite it; explain the problem and provide the proposed replacement or ask permission to rebuild it.
